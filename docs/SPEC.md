あなたは、TypeScriptのSDK設計、AI APIの統合、OSSライブラリの開発・保守に精通したシニアエンジニアです。

以下の方針で、SOM／Decisions専用の汎用ラッパーライブラリを実装してください。設計提案だけで終わらず、初版の実装、テスト、ドキュメント、パッケージ化、公開準備まで進めてください。

将来の機能追加と継続保守の方針も整備してください。ただし、将来機能を初版ですべて実装する必要はありません。

# 1. 背景と目的

3inch.aiはAI活用を扱うメディアです。3inch.ai Labsでは、AIを利用した実用ツールや技術デモを公開していきます。

今回作るライブラリは、今後のLabsのツールで共用しつつ、外部の開発者にも利用してもらうOSSとして公開する予定です。

次の接続先を、共通のTypeScript APIから簡単に切り替えられるようにしてください。

- TypeSafeが提供する公式Jev API
- OpenAI Decisions API
- ローカルで動作するH2O LightningなどのSOM互換HTTPサーバー
- 将来的に登場する、類似の判断APIや互換サーバー

このライブラリの中心的な価値は、次の4点です。

1. TypeScriptアプリから直接利用でき、導入が簡単であること。
2. 接続先の能力を不必要に制限せず、変換できない部分を明確に伝えること。
3. 回答拒否、未対応、応答の欠落、不正な応答を区別できること。
4. 共通の結果に加えて、接続先固有の機能と元の応答へアクセスできること。

利用者にとって有益なライブラリであることを優先してください。3inch.aiへの参照・紹介につながることも目的ですが、機能やドキュメントの品質を中心に設計します。

# 2. 作業の進め方

最初に既存リポジトリ、関連する指示ファイル、実装済みの機能、利用可能な開発環境を確認してください。

既存プロジェクトがある場合は、その構成と公開APIを尊重してください。何もない場合は、小さな独立パッケージとして開始してください。名称が未指定なら仮称を使って進め、公開名やnpmスコープが利用可能であるとは仮定しないでください。

実装前に、対象APIとローカルサーバーの現在の公式仕様を確認してください。過去の調査結果や、このプロンプトに登場する機能名だけを根拠に実装しないでください。

通常の設計判断は、合理的な前提を置いて進めて構いません。重要な前提と判断理由はドキュメントに残してください。APIキーがない場合も、実装やオフラインの検証を完了させ、実接続が未検証であることを明記してください。

コードの変更は今回の目的に集中させ、無関係な大規模リファクタリングは避けてください。

# 3. 初版の実装範囲

初版では、次を実装してください。

## 共通API

中心となる呼び出しは `decide()` ひとつにしてください。

入力は、テキストとJSONを扱えるようにしてください。JSONの表現方法はアダプターの仕様に従い、ネイティブのJSON入力、System Oneのstate、文字列化など、どの形式で送るのかを明記してください。

質問は、名前付きの複数の質問をまとめて渡せるようにしてください。

対応する判定は次の3種類です。

- predicate：条件が真である確率
- choice：指定した選択肢からの選択
- score：順序付きの評価段階に対するスコア

## 初期アダプター

通信形式として、次の2系統を実装してください。

- System One互換
- OpenAI Decisions互換

その上で、公式Jev、OpenAI、ローカルH2O Lightning向けの設定例またはプリセットを用意してください。

ローカル対応は、既存のHTTPサーバーへ接続するところまでです。モデルのダウンロード、起動、量子化、GPU管理、推論エンジンの実装は初版の対象外です。

## 対応環境

標準の `fetch` と `AbortSignal` を中心に、次の環境で使える設計にしてください。

- Node.js
- Bun
- Cloudflare Workers

実際に検証したランタイムとバージョンを記録してください。

初版では、画像、Box、音声、動画、独自ゲートウェイ、管理画面、自動モデル選択、複雑なフォールバックは実装範囲に含めません。

# 4. アーキテクチャと設定

プロトコル、提供者、接続先URL、モデル、実行環境を別々の概念として扱ってください。

例えば、H2O Lightningを利用するために、無関係な提供者名をモデル名へ付けるような公開APIにはしないでください。通信形式、baseURL、モデル名を明示すれば、互換サーバーへ接続できる形を目指してください。

設定はクライアント単位に保持してください。グローバルな設定変更が、別のクライアントの動作へ影響しないようにしてください。

アダプターは、次の責務を担当します。

- 接続先の能力と制限の宣言
- 共通入力から送信形式への変換
- 固有オプションの処理
- 応答の解釈と共通結果への変換
- プロバイダー固有情報の取り出し

通信処理と変換処理を分離し、変換をネットワークなしで検証できるようにしてください。

互換プロトコルの接続先追加は、可能な限り設定やアダプター追加だけで済むようにしてください。ただし、将来の仮想的な用途のために、大きなプラグイン基盤を先に作る必要はありません。

# 5. 入力と返り値の契約

TypeScriptの型を利用し、質問名、判定の種類、選択肢のリテラル型が、可能な範囲で返り値に反映されるようにしてください。

公開型では、安易に `any` を使わないでください。未解釈の元データには `unknown` を使って構いません。

## Predicate

0〜1の真である確率を返してください。

ライブラリが勝手に0.5などの閾値でbooleanへ変換しないでください。閾値による判定を追加する場合は、利用者が明示的に指定する補助機能として分けてください。

## Choice

選ばれた値と、接続先が返した確率分布を保持してください。

文字列とbooleanの選択肢を扱う場合は、`true` と `"true"` を区別してください。内部表現に通常の文字列キーのオブジェクトを使うことで、両者が衝突しないようにしてください。

接続先の形式では区別できない組み合わせは、その接続先に対して明確なエラーを返してください。別の接続先でも使える有効な入力まで、一律に拒否しないでください。

選択肢の名前や説明はモデルの判断へ影響し得るため、無断で意味の異なる名前へ置換しないでください。

## Score

スコアは、順序付き評価段階のインデックスに基づく値として扱ってください。

評価段階の順序、ラベル、返された確率分布を保持してください。返却されたスコアと、必要に応じて計算した検証用の値は区別し、元のスコアを黙って上書きしないでください。

## 確率とconfidence

次の情報を混同しないでください。

- predicateの真である確率
- choice／scoreの確率分布
- プロバイダー固有のconfidence

confidenceは、全モデル共通の正解確率として扱わないでください。提供者由来の値であることと、その意味を確認できる形で保持してください。

未提供の確率を0で補完したり、確率分布を勝手に再正規化したりしないでください。

usageや費用が未提供の場合も、0と区別してください。

# 6. 応答状態とエラーの扱い

少なくとも、次の状態を明確に区別してください。

- 有効な回答が得られた
- 接続先が明示的に回答を拒否した
- 要求した機能に対応していない
- 回答の欠落、型の不一致、値の不整合などがあった

回答の欠落や、質問と違う型の回答を、モデルによる回答拒否へ変換しないでください。

送信前に判明する未対応機能は、既定ではHTTPリクエストを送らず、対象機能・質問・接続先・理由を含む構造化エラーにしてください。対応する質問だけを送る部分実行モードは、将来機能として分けて構いません。

送信後に一部の質問だけが拒否または不正な応答になった場合は、質問単位の結果として表現し、正常に得られた他の回答は保持してください。

回答数、質問ID、回答ID、順序の不整合を黙って修復しないでください。接続先の仕様で順序対応が定義されている場合は、それに従い、確認できる不一致は明示してください。

通信全体の失敗は、型の付いた共通エラーとして扱ってください。認証失敗、レート制限、タイムアウト、呼び出し中断、ネットワークエラー、不正なリクエストなどを区別し、元のHTTPステータスや原因を保持してください。

公開APIで、何を例外として返し、何を質問単位の結果として返すかを一貫させ、READMEに記載してください。

異常な応答に対しては、少なくとも次を検証してください。

- 確率が有限数で、0〜1の範囲内であること
- 選択結果が、指定した選択肢に含まれること
- 質問と回答の種類が対応していること
- scoreの値や分布が、接続先の契約と整合すること

確率合計の検証は、完全な分布を返す契約の接続先に対して行い、丸め誤差を許容してください。部分的な分布を、根拠なく完全な分布として扱わないでください。

# 7. 固有オプションと元の応答

共通APIだけでは表せない機能へアクセスするため、アダプターごとの `providerOptions` など、明示的な拡張経路を用意してください。

利用者が渡したオプションを黙って捨てないでください。処理できない場合は、具体的なエラーまたは警告を返してください。

共通フィールドと固有オプションが衝突した場合は、既定でエラーにするなど、明確な規則を定めてください。上書きする場合は、利用者の明示的な指定を必要としてください。

OpenAIのキャッシュ関連設定など、現在の公式APIで利用可能な固有機能が、指定したのに送信本文から消えることがないようにしてください。

返り値では、次を区別して保持してください。

- 扱いやすい共通の回答
- 元の応答JSON
- プロバイダー固有のメタデータ
- 要求したモデル名と、応答で確認できた実際のモデル名
- 必要なHTTPメタデータやリクエストID

元の応答は、正規化後のオブジェクトから再構成せず、取得時のデータを保持してください。応答本文が不正な場合も、原因調査に必要な情報を失わないようにしてください。

# 8. 通信と依存関係

ランタイム依存は少なくしてください。依存ゼロを無理に達成するために複雑な独自実装を増やす必要はありません。依存を追加する場合は、理由を説明してください。

次を満たしてください。

- `fetch` を注入できること
- `AbortSignal` による中断ができること
- タイムアウト時に、実際の通信を中断できること
- localhostなどのHTTPサーバーへ接続できること
- APIキー不要の接続先を扱えること
- baseURLの末尾やパス結合で、`/v1/v1`などが発生しないこと
- カスタムのURLプレフィックスを壊さないこと
- importしただけで、外部通信や重い初期化が発生しないこと

既定で別モデルや別サービスへフォールバックしないでください。

再試行を実装する場合は、対象、上限、バックオフ、中断時の動作を明示し、初版では必要最小限にしてください。

APIキーや認証ヘッダーを、返り値、例外、通常ログへ露出させないでください。入力内容や元の応答を勝手にログ出力・外部送信しないでください。

ローカルH2Oへの接続は、ライブラリを実行する環境から到達できるHTTPサーバーが存在することを前提にしてください。

# 9. テストと受け入れ条件

実装をそのままなぞるテストではなく、公開APIの契約と、意味が変わってしまう不具合を検出するテストを作成してください。

最低限、次を検証してください。

1. 同じ共通質問定義を、System One形式とOpenAI Decisions形式へ変換できる。
2. predicate・choice・scoreの結果を正しく取り出せる。
3. booleanと文字列の選択肢を区別できる。
4. 質問数や対応機能の制限が、選択した接続先に適用される。
5. 固有オプションが送信本文へ正しく反映される。
6. 処理できないオプションが、黙って無視されない。
7. 明示的拒否と、欠落回答・型不一致が区別される。
8. 不正な確率や、候補外の選択結果を検出できる。
9. 未提供の確率やusageを、勝手に0へ変換しない。
10. 共通結果への変換後も、元の応答と追加情報を確認できる。
11. 中断、タイムアウト、認証失敗、レート制限が適切に扱われる。
12. 複数クライアントの設定が干渉しない。
13. Node.js・Bun・Workers向けのビルドや基本動作を確認できる。

HTTPモックやfixtureによる契約テストと、実際のAPIを呼ぶ試験は分けてください。

fixtureが公式例、実応答、人工的な異常ケースのどれに基づくかを記録してください。実応答由来のfixtureからは、秘密情報や個人情報を除去してください。

APIキーやローカルモデルが利用可能で、実行が許可されている場合は、費用と回数を抑えて接続確認してください。未実行の接続先を「実動作確認済み」と表記しないでください。

モデルの判断精度と、SDKの変換・通信の正しさは別々に評価してください。

# 11. 将来のアップデート方針

以下をロードマップへ記録してください。バージョン番号と実施順は目安であり、実際の需要とAPIの変化に応じて調整して構いません。

## 初版

共通API、3種類の判定、2系統のプロトコル、Jev・OpenAI・H2Oの接続、応答状態の区別、元データ保持、テスト、ドキュメントを完成させる。

## 次の段階

OpenRouterなどの追加APIや、別のローカル互換サーバーを追加する。

新しい接続先を追加するたびに、対応するプロトコル、能力、制限、オプション、応答の違いを確認する。URLを変えて動くはず、という推測だけで対応表へ追加しない。

## その後の候補

実際の用途が確認できたものから、次を検討する。

- 画像入力、質問内の画像、assets
- Box判定
- 質問単位の部分実行
- 上限に合わせた明示的なリクエスト分割
- 簡単なモデル比較用ヘルパー
- 明示設定による再試行・フォールバック

分割やフォールバックは、リクエスト数、費用、モデル、判定結果へ影響するため、実行内容を利用者が確認できる設計にする。

管理画面、独自ゲートウェイ、モデル配布、GPU運用、大規模な評価基盤は、必要性が確認されるまで対象に含めない。

## 安定版への移行

公開API、エラー契約、型、対応表、移行方針が十分に固まった段階で、1.0への移行を検討する。

# 12. API仕様変更と保守の手順

将来の更新でも、次の手順を使えるようにしてください。

1. 既存実装、対応表、未解決課題を確認する。
2. 変更対象の公式仕様と実装を確認する。
3. 既存の利用者へ与える影響を整理する。
4. 必要なfixtureと、変更の意味を検証するテストを追加する。
5. 実装、型、対応表、ドキュメント、CHANGELOGを一緒に更新する。
6. 関連する契約テストとランタイム検証を行う。
7. 検証済み範囲と未検証範囲を明記してリリースを準備する。

対応表には、少なくとも確認日、参照した公式URL、検証したモデルまたはサーバーのバージョンを記録してください。

モデルのエイリアスと、固定バージョンを区別してください。SDKのバージョンが同じでも、接続先モデルの更新で判断結果が変わる可能性を、ドキュメント上で適切に扱ってください。

SemVerの方針を定めてください。型の変更だけでなく、返り値の意味、エラーの分類、既定の動作が変わる場合も、互換性への影響を検討してください。0.x期間の破壊的変更についても、移行方法を明記してください。

依存更新やAPI仕様変更への追随を、無条件の自動リリースにしないでください。契約テストと必要な確認を通してから公開する手順にしてください。

更新のために既存のプロジェクトを作り直すのではなく、変更が必要な部分を絞って保守できる構成にしてください。
